# `문자 디바이스(Character device) v.s. 블록 디바이스(Block device)`

## `문자 디바이스(cdev)`
> 데이터 단위 : `바이트 스트림`처럼 순차적으로 읽고/씀 (예: read(), write())
> 접근 방식 : 보통 `순차 접근` 중심
> 커널 인터페이스 : `struct file_operations` 기반 (`open/read/write/release`, `ioctl` 등)
> 캐시/스케줄링 : 페이지캐시/IO 스케줄러 같은 `블록 계층`을 기본 전제로 하지 않음

### `cdev`를 쓰는 상황(언제 보편적인가)
- 유저 스페이스에 **간단한 API**를 `/dev/xxx` 형태로 노출하고 싶을 때(예: 설정 읽기/쓰기, 상태 조회, 이벤트 수신)
- 장치가 “디스크처럼” 동작하는 게 아니라, **레지스터/메시지/스트림** 형태로 주고받는 데이터가 핵심일 때
- 파일시스템을 올릴 계획이 없고, **read/write/ioctl/poll** 같은 인터페이스가 자연스러울 때

### `cdev`에서 자주 나오는 포인트
- `read()`는 호출될 때마다 “남은 데이터”를 주고, 더 이상 없으면 **0(EOF)** 을 반환하는 패턴이 흔합니다.  
  예를 들어 `cat /dev/hello0`는 EOF를 만나야 종료하므로, 드라이버가 언젠가는 0을 반환하도록(보통 `*off` 기반) 구현합니다.
- `loff_t *off`는 “파일 위치”로, 보통 드라이버 내부 버퍼(예: `text[64]`)의 현재 위치로 해석합니다.  
  `*off`를 갱신하지 않으면 `cat` 같은 프로그램이 무한히 읽게 될 수 있습니다.
- 비동기 이벤트가 있는 장치는 `poll()`/`fasync`를 추가해 **select/epoll**과 연동하기도 합니다.

### 예시
- `/dev/tty*`, `/dev/console`, `/dev/null`, `/dev/random` 처럼 “스트림” 성격
- 이번 챕터처럼 커널 내부 버퍼(`text`)에 대해 유저가 `read/write`하는 형태


## `블록 디바이스(block device)`
> 데이터 단위 : `고정 크기 블록(섹터)` 단위로 처리
> 접근 방식 : `임의 접근(random access)`이 핵심
> 주 사용처 : 파일 시스템이 올라가는 저장장치에 적합
> 커널 인터페이스/계층 : 블록 계층을 통해 `요청(request) 처리, 큐잉, 병합, IO 스케줄링, 페이지 캐시`등과 강하게 연동

### `block device`를 쓰는 상황
- 장치를 **저장장치처럼** 보이게 하고 싶을 때(예: 디스크/SSD/가상 디스크/loop 디바이스)
- “몇 번째 블록”을 읽고/써야 하는 **랜덤 액세스**가 핵심일 때
- 파일시스템(ext4 등)을 올리거나, 파일시스템이 기대하는 **블록 I/O 모델**에 맞추고 싶을 때

### 왜 `block`은 더 “저장장치용”인가
- 블록 계층은 I/O 요청을 **모아서(큐잉) / 합치고(병합) / 순서를 최적화(스케줄링)** 하는 구조를 전제로 합니다.
- 페이지 캐시와 결합되어 “파일시스템 ↔ 저장장치” 경로에서 성능/일관성을 맞추기 좋습니다.

### 예시
- `/dev/sda`, `/dev/nvme0n1`, `/dev/loop0` 처럼 “디스크” 성격

## 한 줄 선택 기준
- “이 장치를 **파일처럼 열어서 바이트 단위로** 다루면 자연스럽다” → 보통 `cdev`
- “이 장치를 **디스크처럼(블록 단위, 랜덤 접근)** 다루고 파일시스템까지 염두에 둔다” → `block device`
